# 기획서 → CDS mock 화면

## 0. 어떤 요청인가

- **새 기획서**(첨부 있음, 처음 보는 기능) → 1단계부터
- **수정 요청**("칩으로 바꿔줘", "컬럼 추가") → 5단계로 바로. 해당 화면만 고친다
- **기획서 갱신**(같은 기능, 새 버전 첨부) → 1~2단계를 하되 이미 있는 화면은 새로 만들지 않고 수정

## 1. 기획서 읽기

`specs/`의 첨부를 Read로 **끝까지** 읽는다. 앞부분만 읽고 시작하면 화면을 빠뜨린다.

- PDF 10쪽 초과 → `pages`로 범위를 나눠 전부 읽는다
- 이미지 기획서 → 화면 단위로 읽고, 글자가 안 보이면 그 부분을 기획자에게 묻는다
- 여러 파일이 있으면 최신 날짜 파일이 기준. 이전 파일과 어긋나면 최신을 따르고 그 사실을 답변에 한 줄로 적는다

## 2. 화면 분해

기획서에 나오는 화면·페이지·팝업·단계를 표로 만든다.

| 화면 | 종류 | 진입 경로 | 주요 요소 |
|---|---|---|---|
| 회원 목록 | 목록 | 좌측 메뉴 | 검색, 상태 필터, 표, 페이지네이션 |
| 회원 상세 | 상세 | 목록 행 클릭 | 정보 카드, 상태 변경, 이력 |

- 다이얼로그·드로어도 **독립 화면 1개**로 만든다. 미리보기에서 따로 확인할 수 있어야 한다
- feature 이름은 kebab-case 영문(`member`, `order-refund`), 화면 이름은 PascalCase 영문
- 화면이 4개 이상이면 이 표를 AskUserQuestion으로 **한 번** 확인한다
  ("이 화면들을 만들까요?" / 선택지: 전부 · 목록과 상세만 · 다시 정리)

## 3. 되물을 것

아래가 기획서에 없으면 **묻는다**(한 번에 최대 4개, 각 항목에 선택지를 제시).
지어내면 기획자가 잘못된 화면을 승인하게 된다.

- 목록: 정렬 기본값, 페이지 크기, 컬럼 정렬 가능 여부
- 상태: 빈 상태 문구, 로딩 표현, 에러 문구
- 액션: 저장·삭제에 확인 다이얼로그가 필요한지, 성공 후 어디로 가는지
- 폼: 필수 입력 항목, 검증 문구, 취소 시 동작
- 권한: 역할에 따라 숨는 항목이 있는지
- 표기: 날짜 형식, 금액 단위, 상태 라벨 문구

묻기에 사소한 것(칩 색, 아이콘 선택)은 가장 단순한 형태로 만들고 `HANDOFF.md`의 "미결"에 적는다.

## 4. 컴포넌트 매핑

기획서 어휘 → CDS 컴포넌트는 [references/mapping.md](references/mapping.md)를 본다.
없는 컴포넌트가 필요하면 조합으로 대체하고 `HANDOFF.md`에 "CDS 부재"로 적는다.

props·variant는 항상 소스에서 확인한다:
`node_modules/@colosseumcoinckr/cds/src/components/<name>.tsx`

## 5. 파일 작성

화면 1개 = 파일 2개. `src/screens/_example/`의 두 파일이 그대로 참조 예시다.

```
src/screens/<feature>/<ScreenName>.screen.tsx   화면
src/screens/<feature>/<ScreenName>.mock.ts      데이터 + 타입
```

`*.screen.tsx` 규칙:

```tsx
export const meta = {
  title: "회원 목록",          // 기획서의 화면 이름 그대로
  spec: "specs/<파일명>",      // 근거 기획서
  description: "한 줄 요약",
  states: ["default", "empty", "loading", "error"],
  frame: "admin",              // 관리자 화면이면 admin, 팝업/단독이면 none
};

export default function MemberListScreen({ state = "default" }: { state?: string }) { … }
```

- `states`에 적은 값은 실제로 분기해야 한다. 목록·상세는 default·empty·loading·error 4종이
  기본, 폼은 default·검증 에러·loading, 다이얼로그는 default 하나로 충분하다
- 데이터는 `*.mock.ts`에서 import한다. 기획서에 예시 데이터가 있으면 그대로,
  없으면 8~12건을 그 도메인답게 만든다(이름·금액·날짜가 실제처럼 보여야 기획자가 판단할 수 있다)
- 한국어 라벨은 기획서 표기를 그대로 옮긴다. 임의로 다듬지 않는다

## 6. 검증

```bash
pnpm check
```

화면 규칙 검사 + 타입 검사. **통과 전에는 완료라고 답하지 않는다.**
실패 메시지가 파일·문제·수정 방법을 알려준다. 미리보기 서버는 이미 돌고 있으므로
저장하면 기획자 화면에 바로 반영된다.

## 7. 인수인계 문서

`src/screens/<feature>/HANDOFF.md`를 만들거나 갱신한다. 개발자가 이 문서만 읽고 옮긴다.

```md
# <feature> — <기능 이름>

기획서: specs/<파일명> (버전·날짜)

## 화면
| 화면 | 파일 | 미리보기 | 상태 |

## 사용한 CDS 컴포넌트
(쉼표로 나열)

## 기획서와 다르게 한 것 / 임시 조합
- **CDS 부재**: <무엇>을 <어떤 조합>으로 대체. 실제 구현 시 확인 필요

## 미결
- <기획자에게 답을 못 받은 것>

## 이관 메모
- `<Screen>.mock.ts`의 `<변수>` → <API 엔드포인트 또는 "미정">
- (라우팅·권한처럼 실제 앱에서 바꿔야 하는 것)
```

## 8. 답변

```
회원 관리 화면 3개를 만들었습니다.

- 회원 목록 — #/member/MemberList
- 회원 상세 — #/member/MemberDetail
- 정지 처리 팝업 — #/member/MemberSuspendDialog

정지 사유를 필수로 받도록 했습니다(기획서에 명시가 없어 가장 흔한 형태로).
탈퇴 회원 노출 여부는 아직 정해지지 않아 목록에서 제외했습니다.
```

파일 경로·명령 출력·컴포넌트 이름은 쓰지 않는다. 화면 이름과 미리보기 주소로만 말한다.
